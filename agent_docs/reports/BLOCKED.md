## ~~🔴 Блокер 2 (исходная формулировка): Колонки детализации (`count_*`) внутренне несогласованы~~

`TESTING_1.md` (Правило 2, «Anti-Lucky-Sum») требует обязательной сверки:
`SUM(count_exact_high) == leaderboard.exact_high_count` и т.д., иначе тест = FAIL.

Но эталонные данные сами себе противоречат по этим колонкам:

1. **Per-round `count_*` ≠ `expected_base_pts`** в той же строке. Из 90 строк
   `16·eh + 12·ex + 8·di + 4·ou` совпадает с `expected_base_pts` только в 52.
   Пример: `larin` тур 4 — base=48, а `16·1+12·4+8·0+4·0 = 64`.
2. **SUM(per-round `count_*`) ≠ `leaderboard.count`** ни для одного игрока:

| user | eh (сумма/LB) | ex | di | ou |
|------|:--:|:--:|:--:|:--:|
| larin | 4 / 2 | 14 / 13 | 7 / 5 | 21 / 20 |
| starchenkov_c | 3 / 1 | 16 / 15 | 8 / 7 | 18 / 16 |
| kuznetsov | 0 / 0 | 9 / 8 | 6 / 5 | 21 / 19 |
| … | (расхождение у всех 10 игроков) | | | |

При этом `base/bonus/total` у тех же игроков сходятся идеально — то есть
проблема изолирована в колонках `count_*`. По итогам `base = 16·eh_LB + 12·ex_LB
+ 8·di_LB + 4·ou_LB` выполняется для `leaderboard`, но не для per-round строк.

**Следствие:** обязательная сверка детализации из `TESTING_1.md` в текущем виде
**невыполнима** при любой корректной реализации бэкенда.

### Предлагаемые решения (выбрать одно)
- **A.** Предоставить исправленный `expected_scores.csv` (per-round `count_*`,
  согласованные с `expected_base_pts`) и/или `leaderboard.csv`.
- **B.** Заменить обязательную сверку детализации на сверку по
  `expected_base_pts` + `expected_bonus*` + `expected_total` + ранги/тай-брейкеры
  (надёжные инварианты), а `count_*` считать справочными (non-authoritative).
- **C.** Уточнить определение `count_*` (кумулятивные vs эксклюзивные; что входит
  в `count_outcome` — все ≥4 очков или только «чистый исход» 4 очка), чтобы
  сделать колонки воспроизводимыми. (Простые кумулятивные/эксклюзивные трактовки
  уже проверены и не подходят.)
