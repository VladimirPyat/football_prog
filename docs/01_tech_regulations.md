# Технический регламент: Роли, сущности, правила

Приложение должно обеспечить прием прогнозов участников и обработку результатов.
Суть Конкурса прогнозов (далее Конкурс) в том, что участники пытаются угадать исход футбольных матчей до их начала. 
По итогам матчей участникам начисляются очки в зависимости от точности их прогнозов. 

Для понимания что вообще должен делать сервис, даю краткую выжимку из правил Конкурса прогнозов.
а) Основные положения. 
Участники конкурса прогнозируют результаты футбольных матчей Российской премьер-лиги. 
Соревнование состоит из 30 туров, в каждом по 8 матчей. Побеждает участник, набравший по итогам 30 туров наибольшее количество очков.
В разных версиях Правил число очков, команд, туров, матчей может отличаться.

Прием прогнозов участников заканчивается за определенное время до начала первой игры (задается организатором). 
Участник, не сдавший прогнозы в срок, получает за тур ноль очков. После окончания приема прогнозов становится доступна таблица прогнозов участников.

После окончания всех матчей, программа производит подсчет очков в соответствии с правилами и формирует таблицу по итогам тура, а также сводная по итогам всех прошедших туров.


## 1. Роли пользователей

### 1.1 Supervisor (Организатор, может встретиться admin)
- Управляет конкурсом: туры, матчи, результаты
- Вводит финальные счета матчей
- Запускает расчет очков
- **Ограничения**: не может менять правила после старта конкурса

### 1.2  Support (Техническая поддержка)
- Полный доступ к БД и системным настройкам
- Может исправлять любые данные (override)
- Назначает Supervisor'ов
- Запускает пересчет всего конкурса

### 1.3 User (Участник)
- Вводит прогнозы на туры
- Видит свои прогнозы до дедлайна (приватно)
- Видит все прогнозы после дедлайна (публично)
- Настраивает контакты (email, VK, TG)

### 1.4 Visitor (Посетитель)
- Анонимный доступ
- Видит лидерборды и результаты
- **Не видит** прогнозы текущего тура до дедлайна

Организатор также может быть участником, если пригласит сам себя. Но вход будет под другим логином
Саппорт прописывается в конфиге, пригласить его технически невоможно. Саппорт назначает организаторов

## 2. Системные сущности


### 2.1 Team (Команда)

```
class Team(Base):
    id: int (PK)
    name: str (unique)         # "Зенит"
    short_name: str            # "ЗЕН"
    logo_url: str | None
```

- Supervisor может добавлять команды в активный конкурс

### 2.2 Match (Матч)

```
class Match(Base):
    id: int (PK)
    round_id: int (FK)
    team1_id: int (FK)         # домашняя
    team2_id: int (FK)         # гостевая
    date_time: datetime
    score1: int | None         # заполняется после матча
    score2: int | None
    status: MatchStatus        # SCHEDULED, POSTPONED, CANCELED, VOID, FINISHED
```

**Статусы матча**:
- `SCHEDULED` — запланирован
- `POSTPONED` — перенесен (можно включить в free tour)
- `CANCELED` — отменен (не учитывается)
- `VOID` — сыгран, но аннулирован (очки = 0)
- `FINISHED` — завершен, результаты подтверждены

**Валидация**:
- `score1, score2 >= 0` и `<= 20`		# 20 (как и другие констранты) не хардкодим, задаем через конфиг
- Одна команда не может играть дважды в одном туре

### 2.3 Round (Тур)

```
class Round(Base):
    id: int (PK)
    number: int (unique)       # 1-total_rounds
    deadline: datetime
    status: RoundStatus        # DRAFT, ACTIVE, CLOSED, CALCULATED, PUBLISHED
    matches_count: int         
```

**Статусы тура**:
- `DRAFT` — создается, можно редактировать
- `ACTIVE` — активирован, прием прогнозов открыт
- `CLOSED` — дедлайн прошел, прием закрыт
- `CALCULATED` — очки рассчитаны
- `PUBLISHED` — итоги опубликованы (immutable)

**Правило 24 часов**:
- Нельзя менять `deadline` менее чем за 24 часа до первого матча тура

### 2.4 Prediction (Прогноз)

```
class Prediction(Base):
    id: int (PK)
    user_id: int (FK)
    round_id: int (FK)
    match_id: int (FK)
    score1: int                
    score2: int                
    
    __table_args__ = (
        UniqueConstraint('user_id', 'round_id', 'match_id'),
    )
```

**Правила**:
- **Batch-only**: либо все матчи тура заполнены, либо ни одного
- **Pre-deadline**: виден только автору и Supervisor
- **Post-deadline**: виден всем (публично)
- Нельзя редактировать после `deadline`

### 2.5 Score (Очки)

```
class Score(Base):
    id: int (PK)
    user_id: int (FK)
    round_id: int (FK)
    
    # Базовые очки
    points_exact: int          # точный счет
    points_diff: int           # разница мячей
    points_outcome: int        #  исход
    
    # Бонусы
    bonus1: int                # за "уникальный" прогноз в туре, которого нет у других - процент от угаданных очков 
    bonus2: int                # за N угаданных результатов в туре + M набранных очков в туре без учета бонусов
    bonus3: int                # участникам с 1, 2 и 3 результатом по очкам (без бонусов) в туре
    
    # Итого
    total_without_bonus3: int
    total_with_bonus3: int
    correct_outcomes: int      # угадано в туре
```

## 3. Основные показатели конкурса (Contest Parameters)

Эти параметры задаются Supervisor до старта конкурса и сохраняются в таблицу `contest_settings`. После старта (`is_locked = TRUE`) редактирование запрещено. Для тестовых целей значения по умолчанию хранятся в отдельном JSON.

### 3.1 Структурные лимиты
- `total_teams`: общее число команд-участниц
- `matches_per_round`: число матчей в одном туре
- `total_rounds`: общее число туров
- `is_round_robin`: флаг "гладкий чемпионат" (каждый с каждым дома и в гостях)

### 3.2 Валидация для "гладкого" чемпионата
Если `is_round_robin = TRUE`, система проверяет математическую связность:
- `matches_per_round == total_teams / 2`
- `total_rounds == (total_teams - 1) * 2`
Пример: 16 команд → 8 матчей/тур → 30 туров.
Для кубковых/смешанных форматов (`is_round_robin = FALSE`) эти проверки отключаются. Supervisor может задавать произвольные лимиты.

## 4. Система начисления очков

Логика сравнения прогноза и результата жестко зашита в коде. В конфигурации хранятся **только числовые значения, пороги и множители**. Это позволяет менять "вес" очков при создании нового конкурса без правки кода.

### 4.1 Базовые баллы (Base Points)
Приоритет начисления строгой: Exact > Diff > Outcome. Начисляется только один базовый тип за матч.

- **Точный крупный счет** (`exact_high_score`): 16 очков
  Условие: `pred == res` И (`abs(diff) >= 3` ИЛИ `sum_goals > 3`)
  Примеры: 3:0, 3:1, 2:2, 3:2

- **Точный счет** (`exact_score`): 12 очков
  Условие: `pred == res` И НЕ крупный счет

- **Разница мячей + исход** (`diff_plus_outcome`): 8 очков
  Условие: `sign(pred_diff) == sign(res_diff)` И `abs(pred_diff) == abs(res_diff)`
  Пример: прогноз 2:1, результат 3:2 (разница +1 у обоих)

- **Только исход** (`outcome_only`): 4 очка
  Условие: `sign(pred_diff) == sign(res_diff)` (победа хозяев / ничья / победа гостей)

- **Не угадал** (`miss`): 0 очков

### 4.2 Бонусы (Bonuses)
Начисляются поверх базовых баллов. Могут быть фиксированными или процентными.

- **Бонус 1: Уникальность прогноза** (`bonus_1`)
  Тип: `% от базовых очков за матч`
  Условие: Если на данный точный счёт в этом матче не поставил никто другой (`count_users_with_this_score == 1`)
  Значение по умолчанию: `100%` (коэффициент 1.0)

- **Бонус 2: Серия угаданных исходов** (`bonus_2`)
  Тип: Фиксированные очки по порогам
  Условие: Общее число матчей в туре, где угадан хотя бы исход (4+ очков)
  Пороги: 6 исходов → 8 очков, 7 → 12 очков, 8 → 16 очков

- **Бонус 3: Место в туре** (`bonus_3`)
  Тип: Фиксированные очки за позицию в лидерборде тура
  Условие: Ранжирование участников по `base_total` (без бонусов 2,3)
  Распределение: 1 место → 12, 2 место → 8, 3 место → 4
  Нюанс: При одинаковых очках все получают бонус соответствующего места. Если `base_total == 0` → бонус 3 не начисляется.
  Дополнительный триггер: +4 очка если `base_total_without_b2_b3 >= 50`
  
### 4.3 Иерархия определения мест (Tie-Breaking Rules) в итоговом лидерборде

При равенстве `total_points` ранжирование происходит строго по следующей цепочке. Логика реализуется в сервисе сортировки, а не в UI.

1. **Основной**: `total_points DESC`
2. **Критерий 2**: `exact_scores_count DESC` (сумма точных счетов за все туры, включая крупные и обычные)
3. **Критерий 3**: `total_without_bonuses DESC` (сумма базовых очков без учета бонусов 1, 2, 3)
4. **Критерий 4**: `correct_diffs_count DESC` (сумма угаданных разниц мячей за все туры)
5. **Fallback**: Если все 4 критерия идентичны → `tiebreaker_status = "manual_override"`. Supervisor вручную назначает приоритетное место через админ-панель. Вероятность крайне мала, эндпоинт обязателен.

⚠️ **Важно**: Бонусы (1, 2, 3) влияют только на итоговую сумму `total_points`, но исключаются из критериев 2-4, чтобы исключить случайность в распределении призовых мест.

## 5. Глобальные правила

### 5.1 Мульти-конкурсность
- Система поддерживает несколько независимых конкурсов
- Каждый конкурс: `Contest(id, name, status, rules_json)`
- Изоляция данных по `contest_id`

### 5.2 Immutable логика
После старта конкурса (первый активированный тур):
- ❌ Нельзя менять систему очков
- ❌ Нельзя добавлять/удалять участников
- ❌ Нельзя менять число туров
- ✅ Можно добавлять команды (для кубков)

### 5.3 Free Tour
- Создается из перенесенных матчей (`status=POSTPONED`)
- Может включать матчи из разных туров
- Отдельный дедлайн
- Матч исчезает из основного тура

### 5.4 Аннулирование (VOID)
- Supervisor может пометить матч как `VOID`
- Все очки за этот матч = 0
- Пересчет лидерборда (транзакция)


## 6. Валидационные правила

### 6.1 Счета матчей
- Целые числа `>= 0` и `<= 20`
- Только для завершенных матчей

### 6.2 Прогнозы
- Целые числа `>= 0` и `<= 20`
- Все матчи тура обязательны
- Нельзя после `deadline`
