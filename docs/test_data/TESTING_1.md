## 🎯 Цель
Гарантировать 100% математическое и логическое совпадение работы бэкенда с историческими верифицированными данными. Любое расхождение в очках или детализации считается критическим багом.

## 📦 Входные данные (test_data/contracted/)
Агент `@Tester` использует следующие файлы для загрузки и верификации:
1. `teams.csv` и `users.csv` — справочники.
2. `predictions.csv` — прогнозы игроков. **ВАЖНО:** Если у игрока нет прогноза на матч/тур, строки в этом файле просто НЕТ. Это не `0:0`!
3. `matches.csv` — единая таблица расписания и результатов. Для несостоявшихся матчей (10 тур) поля `actual_score1` и `actual_score2` содержат пустые значения (`NaN`/`NULL`), а `status` = `SCHEDULED`.
4. `expected_scores.csv` — эталонные очки по каждому туру для каждого игрока, **включая детализацию** (`count_exact_high`, `count_exact`, `count_diff`, `count_outcome`).
5. `leaderboard.csv` — итоговая сводная таблица для финальной перекрестной проверки.
config/contest_defaults.json - установки по умолчанию (число очков, бонусы, распределение мест)

## ⚠️ КРИТИЧЕСКИЕ ПРАВИЛА (Must Know)

### Правило 1: `0` ≠ Отсутствие прогноза
- `0` в поле счета означает, что игрок предсказал 0 голов.
- **Отсутствие прогноза** означает, что в таблице `predictions` для данной пары `(user_id, match_id)` запись отсутствует (`NULL` при JOIN).
- Бэкенд **обязан** проверять `IS NOT NULL`, а не `!= 0`. Иначе игрок получит "фантомные" очки за угаданную ничью 0:0.

### Правило 2: Перекрестная проверка детализации (Anti-Lucky-Sum)
Совпадение итоговой суммы очков недостаточно (ошибка в бонусах может компенсировать ошибку в базе). 
Агент `@Tester` обязан проверить, что для каждого пользователя:
`SUM(count_exact_high) == leaderboard.exact_high_count`
`SUM(count_exact) == leaderboard.exact_count`
`SUM(count_diff) == leaderboard.diff_count`
`SUM(count_outcome) == leaderboard.outcome_count`
Если суммы не сходятся, тест считается **FAILED**, даже если `total_points` совпал.

### Правило 3: Транзакционность и Batch-only
- Прогнозы сохраняются только полным пакетом на тур. Частичное сохранение должно возвращать `400 Bad Request`.
- Пересчет очков при изменении результата матча (или статусе `VOID`) должен быть атомарным для всех участников тура.

## 🔄 Пошаговый алгоритм для @Tester

### Шаг 1: Подготовка окружения
1. Очистить тестовую БД (или использовать изолированную test-базу).
2. Запустить скрипт лоадера: `python test_data/scripts/load_test_data.py --load`.
3. Убедиться, что скрипт завершился с кодом `0` и вывел `✅ Data loaded successfully`.

### Шаг 2: Проверка целостности данных (Sanity Check)
1. Проверить, что количество строк в `predictions` кратно `matches_per_round` (8) для каждого пользователя и тура.
2. Проверить, что в `matches` для 10-го тура поля счетов пусты (`NULL`), а статус `SCHEDULED`.
3. Убедиться, что у пользователя `serov` действительно отсутствуют прогнозы в 4-м туре (как в исходнике).

### Шаг 3: Запуск расчета
1. Вызвать эндпоинт расчета для каждого завершенного тура (1-9):
   `POST /api/v1/admin/rounds/{round_id}/calculate`
2. Убедиться, что статус тура изменился на `CALCULATED` или `PUBLISHED`.

### Шаг 4: Верификация результатов
1. Получить данные через API: `GET /api/v1/rounds/{round_id}/results` и `GET /api/v1/leaderboard`.
2. Для каждого пользователя в каждом туре сравнить:
   - `expected_base_pts` с суммой начисленных базовых очков.
   - `expected_bonus1`, `expected_bonus2`, `expected_bonus3` с начисленными бонусами.
   - `expected_total` с итоговым `total_points`.
3. **Перекрестная проверка**: Сгруппировать `expected_scores.csv` по `user_login`, просуммировать `count_exact_high`, `count_exact`, `count_diff`, `count_outcome` и сравнить с соответствующими колонками в `leaderboard.csv`.

### Шаг 5: Формирование отчета
- Если все проверки пройдены: записать `✅ PASS` в `agent_docs/progress/stage_1_backend.md`.
- Если найдено расхождение: сгенерировать `agent_docs/reports/TEST_REPORT.md` по шаблону ниже и остановить конвейер.
