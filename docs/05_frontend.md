# Инструкция для агента-планировщика: Этап 2 (Фронтенд)

## Цель
Разработать детальный план реализации фронтенда для конкурса спортивных прогнозов. Фронтенд должен визуализировать готовый бэкенд (API v1), соответствовать предоставленным скриншотам и пользовательским сценариям.

## Входные данные (контекст)
Агент должен изучить прилагаемые документы перед планированием:
- **API контракт**
- **Пользовательские сценарии**
- **Схема БД**
- **UI примеры**: скриншоты в проекте ./docs/screens
- **Roadmap**: `roadmap.csv` (этап 2)

## Круг вопросов для учёта при планировании

### 1. Архитектура и стек
- Выбор фреймворка (React), языка (TypeScript), роутинга, state management
- Структура проекта (папки, компоненты, хуки, утилиты)
- Интеграция с API: базовый URL, contest_id в запросах, JWT handling

### 2. Аутентификация и авторизация (RBAC)
- Login/Logout flow, JWT в localStorage
- Force password change при `is_temp_password=true`
- Разграничение доступа по ролям (Visitor/User/SUPERVISOR) на уровне UI и маршрутов
- Auto-logout при 401

### 3. Валидация и бизнес-правила
- Дублирование бэкенд-валидации на клиенте (0-20, обязательные поля)
- Batch-операции (прогнозы: все 8 матчей атомарно, 100% заполнение)
- Дедлайны: проверка на клиенте, таймер обратного отсчёта, readonly после дедлайна
- Правило 24 часов (дедлайн < first_match_date - 24h)
- Immutable UI после `is_locked=true` и активации тура

### 4. Приватность и состояния
- Pre-deadline: User видит свои прогнозы, у других "Прогноз сделан"
- Post-deadline: все видят полную таблицу
- Visitor: всегда заглушка
- Статусы туров (DRAFT/ACTIVE/CLOSED/CALCULATED/PUBLISHED) и матчей (SCHEDULED/POSTPONED/CANCELED/VOID/FINISHED) с цветовой индикацией

### 5. Производительность и UX
- Кэширование лидерборда (Cache-Control + ETag)
- Optimistic updates для прогнозов
- Обработка ошибок (401→redirect, 403→toast, 400→form errors)
- Accessibility (ARIA labels, keyboard navigation)

### 6. Тестирование
- E2E сценарии (Playwright) по UC-7..UC-13
- Визуальные регрессии (сравнение со скриншотами)
- Тесты валидации и RBAC

## Требования к выходным артефактам

### Декомпозиция на подэтапы
Разбить задачу на **4 подэтапа**, например:
1. **Подэтап 2.1**: Аутентификация + Профиль
2. **Подэтап 2.2**: Supervisor UI (настройки, туры, результаты)
3. **Подэтап 2.3**: User UI (Прогнозы + Приватность)
4. **Подэтап 2.4**: Результаты + Лидерборд + Финальная сборка

Для каждого подэтапа подготовить:
- **Человекочитаемый план** (цели, задачи, компоненты, API endpoints, валидация, что должно работать к концу подэтапа, что нужно из предыдущих подэтапов)


### После утверждения
- **Инструкции для Coder**: настройка проекта, примеры кода, API client setup, формы, роутинг guards
- **Инструкции для Tester**: E2E сценарии, визуальные регрессии, тесты валидации и RBAC

### Общие артефакты (создать один раз)
- **Архитектура фронтенда**: стек, структура проекта, роутинг, интеграция с API
- **Контракты интеграции**: детали работы с API v1 (JWT, contest-scoped endpoints, error handling, cache)
- **UI спецификации**: компонентная база, страницы по ролям, валидация, управление состоянием


## Критерии качества планов
- **Полнота**: все API endpoints покрыты, все страницы из сценариев описаны, все компоненты из скриншотов перечислены
- **Соответствие бэку**: валидация дублирует бэкенд, RBAC учтён, immutable логика описана
- **Готовность к реализации**: планы должны быть достаточно детальными, чтобы Coder мог приступить к работе без дополнительных уточнений
- **Тестируемость**: E2E сценарии покрывают все пользовательские сценарии (UC-7..UC-13)

## Приоритет
**Качество > Скорость**. Лучше потратить больше токенов на генерацию детальных планов, чем получить поверхностные документы. Планы должны быть человекочитаемыми. После одобрения создаем инструкции для Coder и Tester.
